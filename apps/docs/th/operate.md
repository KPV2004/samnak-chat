# การดูแลระบบ

หน้านี้อธิบายงานที่ทำหลังเริ่มระบบครั้งแรก ได้แก่ การดูสถานะ การอัปเกรด การสำรองและกู้คืนข้อมูล การอ่านบันทึกและเมตริก และการเปลี่ยนโมดูล คำสั่งทั้งหมดรันจากโฟลเดอร์รากของโครงการ โดยใช้ไฟล์ Compose สำหรับใช้งานจริง และไฟล์ `.env` ที่คุณสร้างตาม[ขั้นตอนติดตั้ง](/th/install)

## คำสั่งที่ใช้ทุกวัน {#commands}

```sh
docker compose --env-file .env -f deploy/compose.prod.yml ps                 # สถานะของแต่ละบริการ
docker compose --env-file .env -f deploy/compose.prod.yml logs -f server     # บันทึกของเซิร์ฟเวอร์ หนึ่งบรรทัดต่อหนึ่ง JSON
docker compose --env-file .env -f deploy/compose.prod.yml down               # หยุดระบบ ข้อมูลยังคงอยู่
```

`down -v` จะลบโวลุ่มด้วย และโวลุ่มเก็บข้อมูลทั้งหมดไว้ ได้แก่ ฐานข้อมูล ไฟล์ และใบรับรอง อย่ารันคำสั่งนี้ เว้นแต่ต้องการลบทุกอย่างจริง ๆ

## อัปเกรด

ดึงโค้ดใหม่ แล้วสร้างอิมเมจใหม่

```sh
git pull
docker compose --env-file .env -f deploy/compose.prod.yml up -d --build --wait
```

บริการ `migrate` รันการย้ายโครงสร้างของโมดูลที่เปิดอยู่ก่อนที่เซิร์ฟเวอร์ใหม่จะเริ่ม ถ้าการย้ายล้มเหลว เซิร์ฟเวอร์จะไม่เริ่ม ข้อมูลเดิมจึงยังอยู่ครบ ถ้า `up` รายงานว่าล้มเหลว ให้อ่านผลลัพธ์ของ `migrate` ด้วย `logs migrate`

หลังอัปเกรด ตรวจเวอร์ชันด้วย เซิร์ฟเวอร์รายงานเวอร์ชันที่ `GET /api/v1/meta` และ[บันทึกการเปลี่ยนแปลง](/th/changelog)บอกว่าอะไรเปลี่ยนไปบ้าง

## สำรองข้อมูล

สำรองสองอย่าง คือฐานข้อมูลกับไฟล์แนบ

**ฐานข้อมูล** คือ dump ของ PostgreSQL แฟล็ก `--clean --if-exists` ทำให้ dump ลบและสร้างตารางของมันขึ้นใหม่ เพื่อให้โหลดทับตารางว่างที่การย้ายโครงสร้างสร้างไว้ได้

```sh
docker compose --env-file .env -f deploy/compose.prod.yml exec -T postgres pg_dump -U samnak --clean --if-exists samnak > samnak-backup.sql
```

**ไฟล์แนบ** อยู่ในโวลุ่ม `miniodata` ให้รวมโวลุ่มนี้ไว้ในการสำรองโวลุ่ม Docker ตามปกติของคุณ

เก็บสำเนาทั้งสองไว้นอกเครื่องนี้ ไฟล์ `.env` มีความลับอยู่ด้วย จึงควรสำรองไปพร้อมกัน

## กู้คืนข้อมูล

การกู้คืนจะแทนที่ข้อมูลในฐานข้อมูลด้วย dump ให้กู้คืนไปยังชุดบริการใหม่ บนเครื่องที่ไม่มีข้อมูลที่คุณต้องการเก็บ

1. เริ่มชุดบริการ เพื่อให้การย้ายโครงสร้างสร้างตารางขึ้นมา

   ```sh
   docker compose --env-file .env -f deploy/compose.prod.yml up -d --wait
   ```

2. หยุดเซิร์ฟเวอร์ เพื่อไม่ให้มีอะไรเขียนข้อมูลระหว่างโหลด dump

   ```sh
   docker compose --env-file .env -f deploy/compose.prod.yml stop server
   ```

3. โหลด dump โหลดได้โดยไม่มีข้อผิดพลาดเมื่อโหลดเข้าชุดบริการที่การย้ายโครงสร้างเพิ่งตั้งค่าไว้

   ```sh
   docker compose --env-file .env -f deploy/compose.prod.yml exec -T postgres psql -U samnak samnak < samnak-backup.sql
   ```

4. เริ่มเซิร์ฟเวอร์อีกครั้ง

   ```sh
   docker compose --env-file .env -f deploy/compose.prod.yml up -d --wait
   ```

ไฟล์แนบเป็นสำเนาแยกต่างหาก ให้คืนเข้าโวลุ่ม `miniodata` ด้วยเครื่องมือเดียวกับที่ใช้คัดลอกโวลุ่มนั้น โครงการยังไม่ได้ทดสอบขั้นตอนนี้

## สุขภาพและสถานะ

เซิร์ฟเวอร์มีจุดตรวจสุขภาพสองจุด

| เส้นทาง | ตอบ |
| --- | --- |
| `GET /healthz` | 200 ตราบที่โปรเซสยังทำงาน |
| `GET /readyz` | 200 เมื่อฐานข้อมูลและ Redis ตอบ มิฉะนั้นตอบ 503 พร้อมชื่อการตรวจที่ล้มเหลว |

ทั้งสองอยู่ที่เซิร์ฟเวอร์ ไม่ได้อยู่ใต้ `/api` และ Caddy ไม่ส่งต่อให้ ดังนั้นจากภายนอกระบบ ทั้งสองเส้นทางจะตอบด้วยหน้าของเว็บแอป ไม่ใช่คำตอบด้านสุขภาพ ภายในระบบ การตรวจสุขภาพของบริการ `server` รัน `/healthcheck` ซึ่งเป็นโปรแกรมเล็ก ๆ ในอิมเมจ และจะออกด้วยค่า 0 เมื่อ `/readyz` ตอบ 200 คุณรันเองได้

```sh
docker compose --env-file .env -f deploy/compose.prod.yml exec server /healthcheck; echo $?
```

`ps` แสดงสุขภาพของแต่ละบริการ ถ้าบริการใดยังเป็น `unhealthy` ให้ดูที่ `logs` ของบริการนั้น

## เมตริก

เซิร์ฟเวอร์เปิดเมตริก Prometheus ที่ `/metrics` เมตริกอยู่ในเครือข่ายภายในเท่านั้น Caddy ไม่ส่งต่อ `/metrics` และไม่มีพอร์ตที่เปิดให้เข้าถึง ถ้าต้องการอ่านจากเครื่องโฮสต์ ให้สั่งผ่านคอนเทนเนอร์ `web` ซึ่งอยู่ในเครือข่ายเดียวกัน

```sh
docker compose --env-file .env -f deploy/compose.prod.yml exec web wget -qO- http://server:8080/metrics
```

เมตริกที่มีได้แก่

- `http_request_duration_seconds` แยกตามรูปแบบเส้นทาง เมธอด และสถานะ การจับเวลาไม่รวมการเชื่อมต่อ WebSocket
- `ws_connections` เกจวัดจำนวนการเชื่อมต่อ WebSocket ที่เปิดอยู่
- `ws_messages_sent_total` เคาน์เตอร์นับข้อความที่ส่งผ่าน WebSocket
- เมตริกของรันไทม์ Go และของโปรเซส

`/metrics` ไม่มีการยืนยันตัวตน นั่นเป็นเหตุผลที่พร็อกซีไม่ส่งต่อเส้นทางนี้

## บันทึก

เซิร์ฟเวอร์เขียนบันทึกเป็น JSON หนึ่งออบเจกต์ต่อหนึ่งบรรทัดไปยัง stdout ใช้ `logs -f server` เพื่อดูแบบต่อเนื่อง หรือส่งผลลัพธ์ไปยังระบบบันทึกของคุณ เมื่อ `SMTP_HOST` ว่าง อีเมลจะถูกเขียนลงบันทึกนี้ ลิงก์ยืนยันและลิงก์ตั้งรหัสผ่านใหม่จึงอยู่ตรงนั้นด้วย เพื่อหาลิงก์ยืนยัน

```sh
docker compose --env-file .env -f deploy/compose.prod.yml logs server | grep verify-email
```

ให้ปฏิบัติต่อลิงก์เหล่านี้เหมือนความลับ ใครที่มีลิงก์ก็ยืนยันหรือตั้งรหัสผ่านใหม่ของบัญชีนั้นได้

## โมดูล

เปลี่ยน `MODULES_ENABLED` ในไฟล์ `.env` แล้วนำการเปลี่ยนแปลงไปใช้ด้วยการรัน `up` อีกครั้ง

```sh
docker compose --env-file .env -f deploy/compose.prod.yml up -d --wait
```

บริการ `migrate` จะสร้างตารางของโมดูลที่เพิ่งเปิด โมดูลที่ปิดไปจะเก็บข้อมูลไว้ และเมื่อเปิดกลับมา ข้อมูลเดิมจะกลับมาให้เห็น ดูค่าได้ที่[การตั้งค่า](/th/configuration#modules)

## งานเบื้องหลัง

เซิร์ฟเวอร์รันงานเหล่านี้เอง ไม่ต้องตั้งค่าเพิ่ม

| งาน | เมื่อไร | ทำอะไร |
| --- | --- | --- |
| ส่งอีเมล พร้อมลองใหม่ | เมื่อมีอีเมลเข้าคิว | ส่งอีเมลสมัครสมาชิก ยืนยัน และตั้งรหัสผ่านใหม่ |
| เตือนงานที่ครบกำหนด | ทุก 5 นาที | แจ้งผู้รับผิดชอบงานที่ครบกำหนดภายใน 24 ชั่วโมง และงานที่เลยกำหนด |
| ล้างการแจ้งเตือน | ทุก 24 ชั่วโมง | ลบการแจ้งเตือนที่อ่านแล้วซึ่งเก่ากว่าประมาณ 90 วัน |
| ล้างเหตุการณ์ที่ส่งแล้ว | ทุกวัน | ลบเหตุการณ์ที่ส่งแล้วซึ่งเก่ากว่า 7 วัน |

งานเหล่านี้ทำงานในฐานข้อมูล PostgreSQL ของเซิร์ฟเวอร์ ดังนั้นการสำรองฐานข้อมูลจึงรวมงานเหล่านี้ไว้ด้วย

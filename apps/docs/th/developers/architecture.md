# สถาปัตยกรรม

หน้านี้เป็นสรุปสำหรับคนที่แก้โค้ด เอกสารฉบับเต็มซึ่งมีแผนภาพและเหตุผลของแต่ละการตัดสินใจอยู่ที่ [`docs/architecture.md`](https://github.com/KPV2004/samnak-chat/blob/main/docs/architecture.md) ในที่เก็บโค้ด และระบุไว้ชัดเจนว่าอะไรเป็นแผนงานที่ยังไม่ได้สร้าง

## รูปร่างของระบบ

Samnak Chat เป็นโปรแกรม Go ตัวเดียว แบบ **โมโนลิธแบบแยกโมดูล** แต่ละฟีเจอร์เป็นโมดูลหนึ่ง และเปิดหรือปิดโมดูลได้ เว็บแอปเป็นไคลเอนต์ React กับ Vite ที่ใช้เฉพาะ API สาธารณะและ WebSocket หนึ่งชุด

```
ไคลเอนต์: เว็บ (React + Vite)          แผนงาน: เดสก์ท็อป (Tauri), มือถือ (Expo)
    │  REST + WebSocket
เซิร์ฟเวอร์ (Go): HTTP API และฮับ WebSocket
    ├── โมดูลหลัก:      auth, workspace, chat
    └── โมดูลเสริม:     notify, task, approval, helpdesk
    │
    ├── PostgreSQL   ข้อมูล ตาราง outbox ของอีเวนต์ และงานเบื้องหลัง (River)
    ├── Redis        presence และการกระจายข้อความระหว่างเซิร์ฟเวอร์หลายตัว
    └── MinIO / S3   ไฟล์แนบ ผ่าน presigned URL
```

ภายในแต่ละโมดูล โค้ดเรียงตาม Clean Architecture: `adapter → usecase → domain` กฎธุรกิจใน `domain` ไม่รู้จัก SQL, HTTP หรือ JSON

## โครงสร้างฝั่งเซิร์ฟเวอร์

| โฟลเดอร์ | เนื้อหา |
| --- | --- |
| `cmd/server` | จุดประกอบระบบทั้งหมด (composition root) ต่อโมดูลเข้าด้วยกันแล้วเริ่มเซิร์ฟเวอร์ |
| `cmd/migrate` | รัน migration ของโมดูลที่เปิดอยู่ |
| `internal/app` | สัญญาที่ใช้ร่วมกัน มีเฉพาะอินเทอร์เฟซและไทป์ ไม่ import อะไรจากโปรเจกต์นี้ |
| `internal/platform` | โครงสร้างพื้นฐาน: การตั้งค่า ฐานข้อมูล Redis ที่เก็บไฟล์ เมล อีเวนต์บัส งาน ขีดจำกัดการเรียก realtime HTTP และเมตริก ไม่รู้จักฟีเจอร์ใด |
| `internal/modules` | หนึ่งโฟลเดอร์ต่อหนึ่งโมดูล |
| `internal/archtest`, `internal/acceptance` | เทสต์การ import ที่ต้องห้าม และเทสต์หลายโมดูลผ่าน HTTP |

## โมดูลคุยกันอย่างไร

โมดูลไม่เรียกโค้ดของกันและกัน ใช้สี่กลไกนี้ เรียงตามลำดับที่ควรใช้

| กลไก | ใช้เมื่อ |
| --- | --- |
| อีเวนต์บัส | ประกาศว่ามีอะไรเกิดขึ้น ผู้ส่งไม่รู้ว่ามีใครฟังอยู่ |
| ทะเบียนการแจ้งเตือน | บอกว่าใครควรได้รับแจ้ง และข้อความว่าอะไร โมดูล notify เป็นผู้ตัดสินว่าผู้ใช้จะได้รับหรือไม่ |
| ทะเบียนการ์ด | แสดงการ์ดในแชท โมดูล chat เก็บและส่งต่อการ์ดโดยไม่อ่านเนื้อใน |
| ทะเบียนบริการ | ขอผลลัพธ์จากอีกโมดูลทันที ใช้น้อยครั้ง |

โมดูลหนึ่ง import ได้เฉพาะ `api.go` และ `events.go` ของโมดูลอื่น

## อีเวนต์และ outbox

อีเวนต์คือสตรักต์ในไฟล์ `events.go` ของโมดูลที่ประกาศ ตั้งชื่อเป็นอดีต เช่น `approval.request_approved` ภายในทรานแซกชันหนึ่ง อีเวนต์จะถูกเขียนลงตาราง `platform_outbox_events` ในทรานแซกชันเดียวกับข้อมูล จึงถูกส่งหลังจาก commit เท่านั้น ถ้าทรานแซกชันถูกย้อนกลับ จะไม่มีอะไรถูกส่ง

การส่งเป็นแบบอย่างน้อยหนึ่งครั้ง (at least once) ผู้รับจึงต้องทำงานซ้ำได้อย่างปลอดภัย ผู้รับที่ล้มเหลวจะถูกบันทึกไว้ และไม่กระทบผู้ส่ง

## ข้อมูล

- ทุกตารางที่เก็บข้อมูลขององค์กรมีคอลัมน์ `workspace_id` use case รับเวิร์กสเปซจากสมาชิกภาพของผู้ใช้ที่เข้าสู่ระบบ ไม่รับจากเนื้อหาคำขอ
- ชื่อตารางขึ้นต้นด้วยชื่อโมดูล เช่น `chat_messages` ไม่มีโมดูลใดอ่านหรือเขียนตารางของโมดูลอื่น
- ID เป็น UUIDv7 เวลาบันทึกเป็น `timestamptz` ใน UTC
- โมดูลอ้างถึงข้อมูลของกันและกันด้วย ID เท่านั้น ไม่มี foreign key ข้ามโมดูล
- Migration อยู่ในโฟลเดอร์ของแต่ละโมดูล และใช้ goose

## ข้อความและ realtime

ข้อความมี `client_msg_id` ที่ไคลเอนต์สร้างขึ้น และฐานข้อมูลจะปฏิเสธสำเนาที่สองจากผู้ส่งคนเดิม เซิร์ฟเวอร์ให้ `seq` แยกตามช่องกับข้อความแต่ละข้อ ความทุกอุปกรณ์จึงเห็นลำดับเดียวกัน หลังเชื่อมต่อใหม่ ไคลเอนต์ขอข้อความหลังจาก `seq` สุดท้ายที่ตัวเองมีผ่าน REST API

WebSocket ไม่เล่นประวัติซ้ำ เซิร์ฟเวอร์แต่ละตัวเก็บการเชื่อมต่อของตัวเองไว้ในหน่วยความจำ และกระจายข้อความผ่าน Redis pub/sub สถานะ presence เก็บใน Redis พร้อมเวลาหมดอายุ และไคลเอนต์ต่ออายุด้วยข้อความ `ping`

## งานเบื้องหลัง

คิวงานคือ River ซึ่งเก็บงานใน PostgreSQL งานจึงถูกเข้าคิวในทรานแซกชันเดียวกับข้อมูลที่มันเป็นของได้ งานตามกำหนดเวลาครอบคลุมวันครบกำหนดของงาน การล้างการแจ้งเตือน และการล้าง outbox การแจ้งเตือนแบบพุชและการตรวจ SLA เป็นแผนงาน ยังไม่ได้สร้าง

## การยืนยันตัวตนและขีดจำกัด

- Access token เป็น JWT อายุ 15 นาที Refresh token อายุ 30 วัน และหมุนเปลี่ยนทุกครั้งที่ใช้ การใช้ refresh token เก่าซ้ำจะเพิกถอนอุปกรณ์ที่เป็นเจ้าของ
- การเข้าสู่ระบบอนุญาตให้พลาดได้ 5 ครั้งต่อนาที ต่ออีเมลหนึ่งรายการและต่อ IP หนึ่งรายการ
- ทุกการเรียก `/api/v1` มีขีดจำกัด: นับตามผู้ใช้เมื่อเข้าสู่ระบบ นับตาม IP ของไคลเอนต์เมื่อไม่ได้เข้าสู่ระบบ ดู[การตั้งค่า](/th/configuration#rate-limits)
- สิทธิ์ถูกตรวจในชั้น use case ด้วย `Authorizer` และโมดูลเพิ่มการกระทำของตัวเองตอนเริ่มทำงาน

## ไฟล์

การอัปโหลดและดาวน์โหลดวิ่งตรงจากเบราว์เซอร์ไปยังที่เก็บอ็อบเจกต์ ผ่าน presigned URL ที่ใช้ได้ 15 นาที เซิร์ฟเวอร์ตรวจทุกการอัปโหลดด้วย `Stat` ก่อนแนบไฟล์เข้ากับข้อความ คำขอ หรือตั๋ว และโมดูลหนึ่งเขียนและลบได้เฉพาะคีย์ของตัวเอง

## ไคลเอนต์

เว็บแอปอยู่ใน `apps/web` ส่วน `packages/core` เก็บ API client ไทป์ที่สร้างจาก OpenAPI และการเชื่อมต่อ WebSocket โดยไม่มีโค้ด DOM หรือเบราว์เซอร์ แอปมือถือที่วางแผนไว้จึงใช้ร่วมได้ ไคลเอนต์แสดงการ์ดตาม `kind` และแสดง `fallback_text` เมื่อเจอ kind ที่ไม่รู้จัก

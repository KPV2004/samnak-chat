# โมดูลและกฎ

Samnak Chat ประกอบขึ้นจากโมดูล หน้านี้ว่าด้วยกฎที่ทำให้โมดูลแยกจากกัน เซิร์ฟเวอร์เริ่มโมดูลอย่างไร และจะเพิ่มโมดูลใหม่ได้อย่างไร คำอธิบายเต็มอยู่ใน [`docs/architecture.md`](https://github.com/KPV2004/samnak-chat/blob/main/docs/architecture.md) หัวข้อ 4 ถึง 7

## อินเทอร์เฟซของโมดูล

ทุกโมดูลทำตามอินเทอร์เฟซ `Module` ใน `internal/app`

```go
type Module interface {
    Name() string
    Requires() []string        // โมดูลที่ขาดไม่ได้สำหรับโมดูลนี้
    Provide(s *Services)       // ระยะที่ 1: เปิดบริการให้โมดูลอื่น
    Init(d *Deps) error        // ระยะที่ 2: สร้าง use case และลงทะเบียนกฎ (ไม่ทำ I/O)
    Routes(api huma.API)       // ลงทะเบียน operation ของ Huma ใต้ /api/v1/{name}
    Subscribe(bus EventBus)    // ฟังอีเวนต์จากโมดูลอื่น
}
```

ตอนเริ่มทำงาน เซิร์ฟเวอร์อ่าน `MODULES_ENABLED` ตรวจว่ามีโมดูลที่จำเป็นครบทุกตัว แล้วเรียงโมดูลตามการพึ่งพา จากนั้นเรียก `Provide` ของทุกโมดูลให้ครบก่อน `Init` ตัวใดจะทำงาน โมดูลจึงค้นหาบริการของกันและกันได้ไม่ว่าจะเรียงลำดับไหน คิวงานและตัวส่ง outbox เริ่มเป็นตัวสุดท้าย handler ทุกตัวจึงลงทะเบียนเสร็จก่อนอีเวนต์หรืองานแรกจะทำงาน

ถ้าโมดูลที่จำเป็นขาดไป เซิร์ฟเวอร์จะหยุดตอนเริ่มพร้อมข้อความบอก ส่วน endpoint ของโมดูลที่ปิดอยู่จะไม่ถูกติดตั้งเลย จึงตอบ 404

## โครงสร้างของโมดูล

```
approval/
├── module.go            # ต่อ adapter เข้ากับ use case และลงทะเบียนกับระบบ
├── api.go               # อินเทอร์เฟซที่โมดูลอื่นเรียกได้
├── events.go            # อีเวนต์ที่โมดูลนี้ประกาศ
├── domain/              # เอนทิตีและกฎธุรกิจ
├── usecase/             # ขั้นตอนการทำงานและพอร์ต (อินเทอร์เฟซที่ต้องการ)
├── adapter/
│   ├── http/            # handler และรูปแบบ JSON
│   ├── postgres/        # repository ที่เขียนด้วย sqlc
│   └── wire/            # ประกอบ adapter ให้ module.go
└── migrations/          # migration ของตารางในโมดูลนี้
```

โมดูลง่าย ๆ ไม่จำเป็นต้องมีทุกชั้น อินเทอร์เฟซถูกสร้างเฉพาะจุดที่มีขอบเขตข้ามผ่าน คือ ฐานข้อมูล อีเวนต์ และโมดูลอื่น

## กฎ

กฎเหล่านี้ทำให้โมดูลแยกจากกัน แต่ละข้อถูกตรวจด้วยเครื่องมือหรือตอนรีวิว

| กฎ | ตรวจอย่างไร |
| --- | --- |
| `internal/app` ไม่ import อะไรจากโปรเจกต์นี้ | `depguard` ใน golangci-lint |
| `internal/platform` ไม่รู้จักฟีเจอร์ จึงไม่ import `internal/modules` | `depguard` ใน golangci-lint |
| โมดูล import ได้เฉพาะ `api.go` และ `events.go` ของโมดูลอื่น | `internal/archtest` ซึ่งรันโดย `go test` |
| ไม่มีโมดูลใดอ่านหรือเขียนตารางของโมดูลอื่น ชื่อตารางขึ้นต้นด้วยชื่อโมดูล | รีวิวและ acceptance test |
| `workspace_id` มาจาก `Principal` ของผู้ใช้ที่เข้าสู่ระบบ ไม่ใช่จากเนื้อหาคำขอ | รีวิวและ acceptance test เรื่องการแยกเวิร์กสเปซ |
| ID เป็น UUIDv7 เวลาบันทึกเป็น `timestamptz` ใน UTC | รีวิว |
| สัญญาใน `internal/app` เปลี่ยนได้เมื่อผู้ดูแลอนุมัติเท่านั้น | รีวิว |

ภายในโมดูล การพึ่งพาไปทางเดียว: `adapter → usecase → domain` ชั้น domain เก็บเอนทิตี การเปลี่ยนสถานะ และข้อผิดพลาดทางธุรกิจ ไม่มี SQL ไม่มีแท็ก HTTP หรือ JSON และไม่เรียกโมดูลอื่น

ถ้าคุณต้องเปลี่ยนสัญญาใน `internal/app` ให้อธิบายปัญหาใน pull request ก่อน อย่าเปลี่ยนสัญญาใน pull request เดียวกันโดยไม่ถาม

## การเพิ่มโมดูล

1. สร้าง `internal/modules/<name>` ด้วยโครงสร้างข้างบน
2. เขียน `module.go` ให้ทำตาม `Module` และระบุโมดูลที่ต้องใช้ใน `Requires()`
3. เพิ่ม migration โดยชื่อตารางขึ้นต้นด้วยชื่อโมดูล
4. ประกาศอีเวนต์ใน `events.go` ลงทะเบียนกฎการแจ้งเตือนและ kind ของการ์ดใน `Init`
5. เพิ่มโมดูลในรายการของ `cmd/server/main.go`
6. เพิ่มโมดูลในเมทริกซ์ `modules` ของ `.github/workflows/ci.yml` เพื่อให้ CI เริ่มเซิร์ฟเวอร์พร้อมโมดูลนั้น

โมดูลที่สร้างแบบนี้ไม่ต้องแก้ไฟล์ในโมดูลอื่นเลย

## โมดูลและฟีเจอร์

| โมดูล | ประเภท | หมายเหตุ |
| --- | --- | --- |
| `auth` | หลัก | บัญชี เซสชัน อีเมล |
| `workspace` | หลัก | เวิร์กสเปซ สมาชิก คำเชิญ กลุ่ม บันทึกการดำเนินการ และ `Authorizer` ที่โมดูลอื่นใช้ |
| `chat` | หลัก | ช่อง ข้อความ เธรด ปฏิกิริยา ไฟล์แนบ คำสั่ง `/` และการกระทำของข้อความ โมดูลอื่นเพิ่มคำสั่งและการกระทำผ่าน `ChatExtensions` |
| `notify` | เสริม | การแจ้งเตือน การตั้งค่า และการส่งผ่าน WebSocket |
| `task` | เสริม | งาน การเตือนความจำ และคำสั่ง `/task` |
| `approval` | เสริม | คำขอ การตัดสินใจ และผู้อนุมัติเริ่มต้นของกลุ่ม |
| `helpdesk` | เสริม | คิว หมวดหมู่ ตั๋ว ความคิดเห็น และคำสั่ง `/ticket` |
